## 2. 业务背景与问题定义

### 2.1 露天矿场景中的数据挑战

露天矿感知训练面临以下数据侧问题：

1. **长尾场景明显**：常规矿道数据量大，而破碎站、充电站、地面积水、扬尘、料堆等关键作业场景样本少。按原始比例训练，模型容易偏向常规道路。
2. **传感器失效更常见**：粉尘、泥污、震动和遮挡可能造成相机局部不可用或 LiDAR 通道缺失。若训练没有覆盖此类工况，模型容易过度依赖单一模态。
3. **时序模型依赖数据顺序**：模型通过跨帧 buffer 利用时序信息；一旦采样器打散 scene 内连续帧，时序建模的输入前提被破坏。
4. **Occupancy 监督存在隐性失效风险**：标签路径未绑定、mask 为空、HR/LR 标签不匹配等问题，可能不会让训练直接报错，却会造成无效监督、零梯度或指标误判。
5. **指标掉点可能来自口径而非模型**：训练配置、传感器 drop、NMS、评测区域或 score 协议不一致，都可能使模型表现出现不可直接比较的变化。

### 2.2 需要交付的闭环能力

| 闭环阶段 | 要解决的问题 | 交付标准 |
|---|---|---|
| GT 生产 | 原始稀疏点云如何成为可训练 Occupancy 标签 | 标签、mask、坐标、语义映射和保存格式正确 |
| 数据组织 | 如何减少常规样本主导、强化长尾场景 | 多源 pkl 可拼接，升降采样可配置且可复现 |
| 时序采样 | 如何让模型拿到连续轨迹而非随机帧 | scene 内连续帧在 batch slot 中保持连续消费 |
| 鲁棒性训练 | 如何覆盖相机/LiDAR 缺失等现场工况 | scene 级缺失模式跨帧一致、跨 epoch 可变 |
| 标签治理 | 如何避免“训练在跑但没有监督” | 标签缺失分类、兜底/补绑/剔除方案可执行 |
| 评测回流 | 如何确认改动服务于真实指标 | 训练输入、采样范围和评测协议可追溯、可对齐 |

## 4. 技术闭环与实施过程

## 4.1 阶段一：构建可训练的 3D Occupancy GT

### 目标

将多路 LiDAR 点云、人标 3D 框和 lidarseg 语义，生成每个关键帧可用于训练的 `labels.npz`。单帧点云只覆盖可见表面且十分稀疏，需要在不引入动态重影和错误自由空间的前提下进行多帧融合。

### 技术流程

#### 4.1.1 帧收集与数据窗口

- 以关键帧为训练标签单元；
- 同时收集当前关键帧、邻近关键帧与 sweep 静态点；
- 邻帧按距离窗口筛选，并设置最小/最大邻帧数，兼顾停车时的样本数量与运动时的几何一致性；
- 对 sweep 设置上限，避免内存和运行时间失控。

#### 4.1.2 动静分类：决定哪些点允许跨帧融合

将目标统一为以下运动状态：静态刚体、动态刚体、非刚体、扬尘、未知。

- 对可追踪实例，使用跨帧 3D 框中心位移除以时间间隔计算速度，并取中位数作为稳健速度判据；
- 使用 0.5 m/s 作为动静阈值，基于 5 个场景、69 个实例的观测进行标定；
- 挖机、装载机、破碎锤等非刚体设备即使短时静止，也不纳入跨帧静态融合；
- 将原本散落在多处的类别名单收敛到统一模块，减少逻辑漂移。

**关键认知**：跨帧融合不能仅按“当前是否在动”判断。非刚体机械局部结构会发生变化，跨帧累积会形成几何拖影，必须在数据侧排除。

#### 4.1.3 位姿粗配准与 ICP 精配准

- 先利用 LiDAR—ego—world—target LiDAR 坐标链完成粗配准；
- 使用 Open3D point-to-plane ICP 做局部几何校正；
- 在矿区场景中对 ICP 修正施加约束，避免 yaw/xy 漂移扩大；
- 记录 fitness、inlier RMSE 等诊断信息，支撑异常配准分析。

#### 4.1.4 ray-casting 构建可监督区域

通过 `lidar_mask` 定义“当前关键帧射线可达”的体素集合：

- 从传感器原点到无遮挡表面之间的自由空间可作为负监督；
- 可见表面体素可作为正监督；
- 被遮挡和从未观测的区域不参与监督；
- 自车区域显式排除。

这一步区分了“空间中没有占用”与“当前帧没有可靠观测”两种完全不同的状态，避免错误的 CrossEntropy 监督。

#### 4.1.5 分层融合、体素化和标签空间解耦

| 层级 | 数据来源 | 策略 |
|---|---|---|
| 权威层 | 当前帧观测、人标框内点 | 保持当前时刻最可信占用，不被低可信来源覆盖 |
| T1 | 邻帧/Sweep 与既有体素重合点 | 只校正已有体素标签，不新增占用 |
| T2 | mask 内静态点 | 需满足距离、非刚体保护和多帧见证约束后增密 |
| T3 | mask 外候选点 | 通过球面遮挡、距离和见证机制进行保守补充 |

体素冲突采用：**人标框点 > 当前帧 > 邻帧 > Sweep** 的优先级。内部逻辑保留原始 72 类语义，写盘前再映射为下游训练使用的 7 类，使 GT 生产逻辑与训练标签体系解耦。

### 阶段产出与验证

- 覆盖 **259 场景、14,008 关键帧、148,005 标注框**；
- 使用 **6 worker 并行**执行全量生成；
- 阶段性 V10 与 V3 对比：10 个场景、260 个共有关键帧上的 Occupancy IoU 均值为 **0.4070**；V10 相比 V3 净新增约 **1,850 万体素**；
- 发现并记录 ICP 变换累积、球面深度图跨 ±π 等高危问题，形成后续修复清单。

## 4.2 阶段二：多 pkl 数据集接入与场景分布控制

### 问题

GT 可用后，训练数据仍可能因场景比例失衡而偏向常规道路。数据还来自不同目录和不同产出批次，需要统一、可复现的接入方式。

### 实施方案

维护 `(path, repeat)` 多 pkl 配比机制：

- `repeat ≥ 1`：整份复制，用于升采样；
- `0 < repeat < 1`：保留 `round(n × repeat)` 帧，用于确定性降采样；
- `repeat ≤ 0`：跳过该 pkl；
- pkl 按既定顺序加载，可跨多个目录组合；
- 降采样不依赖全局随机状态，保证相同输入在跨机器、跨 epoch 下结果稳定。

### 数据资产结果

训练集接入 **34 条 pkl 场景源**，配比覆盖 **0.5×～5×**：

| repeat | 数量 | 数据策略 |
|---:|---:|---|
| 0.5 | 6 条 | 降低过量常规道路样本 |
| 1 | 16 条 | 保持常规场景分布 |
| 2 | 2 条 | 轻度补强 |
| 3 | 7 条 | 强化稀缺作业场景 |
| 5 | 3 条 | 强化破碎站、充电站等极长尾场景 |

### 这一阶段的价值

将“依赖人工经验挑数据”转化为可配置的数据分布控制旋钮。后续若发现某个 badcase 场景不足，可以定位对应 pkl 并调整 repeat，而不需要重写数据集代码。

## 4.3 阶段三：scene 级时序采样与 epoch 预算治理

### 问题

时序 BEV 模型的上下文由模型 buffer 维护，因此数据采样必须使同一 batch 槽位在相邻 iteration 中尽可能获得同一 scene 的相邻帧。若随机采样，模型会接收到跨 scene 的无关状态。

### 实施方案

1. **scene 切分**：以样本 `idx` 的变化确定 scene 边界。
2. **slot round-robin**：`samples_per_gpu` 对应多个 slot；每个 slot 认领一个 scene 并逐帧消费，scene 结束后领取下一条 scene。
3. **slot-tail hold**：不同 scene 长度不一致时，用当前 slot 的上一帧回填，保证 batch 形状稳定。
4. **padding 策略**：训练样本数需要对齐分布式卡数时，优先复用最后一个 scene 的最后一帧，并复用同一份 IDA/BDA/Occ 配置，减少时序跳变。
5. **epoch 预算重算**：基础采样与 CBGS 采样均按实际总样本数重新计算每 rank 的 `num_samples`，保证多卡训练的 step 数正确。
6. **异常样本容错**：pipeline 失败的样本记录到错误索引，并优先从同 scene 候选池替换，降低坏样本反复触发概率。

### 关键公式

```text
num_samples = ceil(N / num_replicas / samples_per_gpu) × samples_per_gpu

CBGS 开启后：
N' = 均衡后抽中 scene 的总帧数
num_samples = ceil(N' / num_replicas / samples_per_gpu) × samples_per_gpu
```

### 关键洞察

对时序模型而言，采样器不是普通“数据加载器”，而是时间上下文的组成部分。数据侧若破坏帧序，再强的时序结构也无法获得正确输入。

## 4.4 阶段四：长尾类别均衡与传感器鲁棒性训练

### 4.4.1 scene 级 CBGS 类别均衡

普通单帧重采样会破坏时序连续性，因此采用完整 scene 为最小单位的 CBGS：

- 按类别统计满足命中帧阈值的候选 scene；
- 以 scene 为单位有放回采样，并展开其完整帧序；
- 通过目标 `length_factor` 反解 λ，使 epoch 长度保持可控；
- 使用 `seed + epoch` 控制随机性，支持可复现 A/B；
- 对每类采样比例设置上限，避免极少数场景无限重复；
- 通过硬断言与 region-balance 互斥，防止两种策略同时改写样本预算和索引分布。

```text
λ = (length_factor × N_orig) / n_prime_base
```

**为什么不硬编码 λ**：当 pkl 数、候选类别或命中阈值变化时，固定 λ 会导致 epoch 长度不可预测；反解后，`length_factor` 成为业务可解释的“训练预算旋钮”。

### 4.4.2 scene 级互斥传感器 Drop

针对矿区相机污染、遮挡和 LiDAR 缺失，构建/核验 scene 级缺失策略：

- 每个 epoch 重建 scene drop 表；
- 同一 scene 所有帧共享同一份 drop 配置；
- 支持 `img / lidar / none` 三态互斥；
- 支持逐相机 mask，并设置至少保留一路相机的保护；
- LiDAR drop mask 写回并供时序帧复用，保证跨帧模态状态一致；
- 图像缺失以置黑和保留固定相机 slot 的形式实现，维持输入 shape 契约。

**为什么必须是 scene 级而不是逐帧随机**：逐帧随机会让同一轨迹中模态状态不断跳变，模型学到的是噪声而非真实故障模式；scene 级策略更符合“一段作业过程中传感器持续受遮挡”的现场情况。

### 4.4.3 增强开关核验

对 pipeline 做“代码存在—配置声明—实际生效”三层检查：

- 实际运行的关键图像增强为 IDA（resize/crop）；
- 时序一致 IDA/BDA 配置处于启用状态；
- BDA 的部分参数为恒等变换；
- 相机外参扰动、跨模态遮挡、近物体点云丢弃等算子已实现但处于注释关闭状态。

该项工作的价值在于避免“配置里写了某能力”被误认为“训练真正使用了该能力”。

## 4.5 阶段五：Occupancy 标签审计与监督治理

### 问题

训练不报错并不代表监督有效。Occupancy 监督的缺失可能表现为 mask 为空、路径未绑定、HR/LR 标签不匹配等静默问题，最终造成 loss 无效或训练算力浪费。

### 审计结果

| 问题类型 | 审计规模 | 影响 |
|---|---:|---|
| LR `lidar_mask_fine` 为空 | 22 个 pkl、706,821 帧，约 39% | 部分精细 Occupancy loss 缺少有效监督 |
| LR `occ_path` 未绑定 | 8 个 pkl、76,662 帧 | 训练侧跳过相关 Occupancy 监督 |
| HR 部分帧未绑定 | 15 个 pkl、7,634 帧 | 高分辨率监督不完整 |
| LR 与 HR 双缺 | 8 个 pkl、76,662 帧 | 无可用 Occupancy 监督，应避免参与训练 |

> 注：不同统计口径分别描述 LR mask 为空、路径未绑定和双缺样本，不能简单相加后再作为唯一总量对外表述。

### 分型治理策略

| 场景 | 处理策略 | 理由 |
|---|---|---|
| LR mask 缺失、HR 标签存在 | 从 HR 标签降采样兜底 LR mask | 复用已有数据资产，避免无效监督 |
| HR 路径缺失 | 使用“只补缺”的 rebind 方案，先 dry-run | 避免全量重生成和误覆盖已有正确数据 |
| LR/HR 双缺 | 建议从训练集剔除 | 防止无监督样本消耗算力、污染 loss 统计 |
| 配置 root 与实际绑定路径漂移 | 从解析函数、pkl 字段和真实文件三端核对 | 防止配置看似正确但运行静默取错路径 |

### 关键验证

验证 HR→LR 降采样兜底路径：从 HR `1024×1024×128` 的 mask 以 xy 2:1、z 4:1 的 any 规则生成 LR `512×512×32` mask，ground 命中率达到 **99.2%**。这证明该路径可作为训练不中断时的降级方案，但不替代长期的 GT 资产修复。

## 4.6 阶段六：训练—评测口径核验与问题回流

### 问题

指标变化不一定意味着模型本身变好或变坏。训练配置、测试 pipeline、NMS、空间评测区域和 score 公式不一致，都会造成“掉点”或“涨点”的假象。

### 核验内容

- 训练 pipeline 与测试 pipeline 的算子、输入 key 和传感器使用方式；
- 采样区域与评测区域的边界是否一致；
- `final_score` 的区间权重是否跨版本改变；
- 传感器 drop 策略是否与基线一致；
- 挖机、半挂等类别的 NMS 是否对齐；
- backbone 冻结状态是否满足下游模型的特征契约。

### “28 vs 43”掉点事件中的数据侧认识

一次新框架训练的指标相较历史版本从约 43 降至约 28。复盘表明这是多因素叠加：

1. SECOND backbone 被解冻，破坏下游依赖的特征分布；
2. 新旧框架的传感器 drop 策略不一致；
3. 挖机、半挂等类别的 NMS 与评测口径未对齐。

我的贡献是参与定位数据侧的 scene 级 drop 和训练/评测口径问题，并将其转化为可核对清单。这个案例的结论是：**训练策略、数据策略和评测协议必须成对演进，否则指标不可直接归因。**

## 6. 面试讲述稿

### 6.1 90 秒精简版

> 在训练侧，我维护了 34 路 pkl 的确定性配比机制，用 0.5 到 5 倍的升降采样缓解普通矿道与破碎站、充电站等长尾场景的不均衡；同时维护 scene 级时序采样，让同一 batch slot 持续消费同一 scene 的连续帧，避免时序 buffer 跨轨迹跳变。  
>
> 最后，我对 Occupancy 标签做全量审计，发现 LR mask 空监督约占 39%，并有 76,662 帧 LR/HR 双缺样本。我将问题分成可兜底、可 rebind 和需要剔除三类，并验证 HR 降采样补 LR 的可用性。这个项目让我形成了一个认知：感知模型的上限很大程度上取决于数据监督是否可信、采样是否符合时序假设，以及训练和评测是否处于同一口径。

### 6.2 3—4 分钟完整版

> 我参与的是矿区自动驾驶多传感器时序感知的数据闭环建设项目，服务于多任务时序 BEV 感知和 3D Occupancy 模型。我的工作重点不是设计主干网络，而是解决模型训练前后最容易被忽略的数据问题：GT 是否可信、数据分布是否合理、时序输入是否连续、传感器缺失是否符合现场工况，以及训练和评测是否可以在同一口径下比较。  
>
> 项目首先面对的是 Occupancy GT 生产问题。单帧 LiDAR 很稀疏，且矿区中有挖机、装载机、扬尘等复杂目标，不能直接把多帧点云叠加。因此我参与的 GT 链路会先进行动静分类，排除动态和非刚体物体，再通过位姿链与 ICP 做点云对齐。随后用 ray-casting 生成可监督 mask，只在传感器射线可达区域监督 Occupancy；最后再进行分层融合和体素化，其中当前帧和人标框点优先级最高。该链路覆盖 259 个场景、14,008 个关键帧，并通过 6 worker 并行全量运行。  
>
> GT 生成后，第二个问题是训练数据分布。常规矿道数据很多，破碎站、充电站、积水、扬尘等风险场景很少。我维护了 34 路 pkl 的多源数据组织和确定性配比机制，通过 0.5 到 5 倍的 repeat 做升降采样。这个机制的关键不是简单复制，而是保证相同配置在跨机器、跨实验时结果可复现，便于做 A/B。  
>
> 第三个问题是时序正确性。因为模型的时序状态来自 buffer，如果采样器随机打散 scene 内帧，模型拿到的就是跨轨迹状态。我重点维护 scene 分组、slot round-robin、padding 和 epoch 预算逻辑，让同一 batch 槽位尽可能连续消费同一 scene 的帧。对于长尾均衡，我采用 scene 级 CBGS，而不是单帧过采样，以避免破坏时序完整性。  
>
> 第四个问题是矿区实际的模态失效。我参与实现和核验 scene 级传感器 Drop：同一 scene 的相邻帧共享相同的相机或 LiDAR 缺失配置，使模型看到更接近真实故障持续状态的输入，而不是逐帧随机跳变。  
>
> 最后是标签治理和评测回流。我对 Occupancy 标签做全量审计，发现 LR mask 空监督约占 39%，并有 76,662 帧 LR 和 HR 同时缺失。针对不同问题，我没有采用全量重跑，而是分别使用 HR 降采样兜底、只补缺 rebind 和剔除无监督样本的策略。与此同时，我检查训练与测试 pipeline、采样区与评测区、NMS 和 score 协议的差异，参与定位了历史掉点事件中数据策略和评测口径不一致的问题。  
>
> 这段经历的核心价值是：我把 GT 生产、训练数据组织、时序采样、标签审计和指标归因串成了一个可验证的数据闭环，使模型迭代不再只是“改配置再看分数”，而是每一步都有数据依据和可追溯的影响范围。

## 7. 高频技术追问与回答框架

### Q1：为什么 Occupancy 监督需要 ray-casting mask？

**回答框架**：

> 点云没有打到不等于空间为空，可能是遮挡、距离、反射或视场问题。ray-casting mask 定义的是从当前传感器原点到无遮挡表面的“可靠观测区域”：射线经过区域可作为自由空间监督，表面体素可作为占用监督，未观测区域不参与 loss。这样可以避免把未知区域错误当成负样本。

### Q2：为什么不把所有多帧点云直接拼起来？

**回答框架**：

> 直接拼会引入两个问题：动态目标会产生重影，非刚体设备会因自身形变产生错误几何。我的处理方式是先用运动状态分类过滤动态和非刚体对象，再进行配准；融合时还会区分当前帧、邻帧和 sweep 的可信等级，并通过可见性、距离、非刚体保护区和多帧见证来控制增密。

### Q3：scene 级采样为什么比随机采样重要？

**回答框架**：

> 时序模型依赖前序状态。如果随机采样，前一 iteration 的 buffer 可能来自另一条轨迹，当前帧再读取它就没有物理意义。scene 级 slot 流式采样保证同一 slot 在连续 iteration 中尽可能消费同一 scene 的相邻帧；padding 也要复用同 scene 尾帧和相同增强配置，避免制造时序跳变。

### Q4：CBGS 为什么以 scene 而不是 frame 为单位？

**回答框架**：

> 单帧采样确实能提升类别频率，但会破坏时序连续性。scene 级 CBGS 将完整 scene 作为最小复制单位，既提高含稀有类别场景的出现概率，又能保持这条轨迹内部帧序。它与按实例或单帧补样的 region-balance 在目标上不同，因此需要互斥。

### Q5：λ 为什么反解而不是写死？

**回答框架**：

> 候选 scene 数、scene 长度和命中阈值改变后，固定 λ 会导致一个 epoch 的训练量不可预测。反解 λ 后，我可以以 `length_factor` 表达期望 epoch 长度倍率，训练时间和采样强度都更可控，实验之间也能比较。

### Q6：为什么传感器 Drop 要做成 scene 级？

**回答框架**：

> 真实矿区的相机污染或 LiDAR 异常通常会持续一段时间。逐帧随机 Drop 会导致同一轨迹中模态状态频繁切换，既不真实也破坏时序。scene 级 Drop 让连续帧共享同一故障模式，每个 epoch 再改变不同 scene 的缺失配置，能兼顾时序一致性和长期覆盖。

### Q7：`None` 和空集合的 drop mask 为什么要区分？

**回答框架**：

> `None` 表示 scene 级策略尚未决策，应交给后续逻辑按逐帧策略处理；空集合表示 scene 级已经明确决策“本帧/本 scene 不丢任何 LiDAR”。如果代码只按真假判断，会把“明确全保留”误当作“未决策”，重新触发随机 Drop，破坏时序一致性。

### Q8：如何判断是标签问题还是模型问题？

**回答框架**：

> 我会从监督链路反查：先看 pkl 是否绑定 `occ_path`/`occ_path_hr`，再检查 npz 内容和 mask 是否为空，然后看 loader 缺失时是否会把 loss 置零或跳过。将问题分为可由 HR 兜底、路径可 rebind、LR/HR 双缺三类后，才能判断需要修数据、修绑定还是剔除样本，而不是直接把异常归因给模型。

### Q9：如何解释 V10 GT 更稠密但不直接说“更好”？

**回答框架**：

> 更稠密只说明新版本写入了更多体素，不代表新增体素全部正确，也不代表下游模型必然提升。GT 版本验证至少要包括输出完整性、语义和几何契约检查、逐帧差异分析，以及在固定训练和评测配置下的下游效果验证。

### Q10：配置文件能否代表模型实际运行逻辑？

**回答框架**：

> 不能。配置只是声明，必须沿着 builder、注册逻辑、pipeline 和真实输入输出继续验证。例如两个 sampler 开关可以同时写为 True，但 builder 是 `elif`，最终只会构建前一个分支；某些增强配置也可能因参数为恒等值或 pipeline 被注释而没有实际生效。

### Q11：历史“28 vs 43”掉点事件的教训是什么？

**回答框架**：

> 不要把指标变化简单归因于模型结构。该事件中存在 backbone 冻结状态、传感器 Drop 策略和 NMS/评测口径等多项变化。正确做法是把训练策略、数据策略、评测协议和后处理逐项对齐，并将这些配置纳入版本管理。

### Q12：如果重做一次，优先优化什么？

**回答框架**：

> 我会先做训练前数据质量门禁。因为无监督或错监督样本会消耗算力并污染 loss 统计，后续再怎么调采样或模型都难以得到可靠结论。建议在训练启动前自动输出标签覆盖率、双缺样本数、采样预算、drop 分布和训练/评测协议版本。

## 9. 复盘：可沉淀的方法论

1. **先验证监督，再讨论模型。** 标签路径、mask 覆盖和 loss 是否生效，应成为训练前检查项。
2. **时序模型的数据顺序是模型输入的一部分。** sampler、padding 和增强复用不能按普通图像任务的思路处理。
3. **“配置写了”不代表“能力生效”。** 必须验证配置、builder、pipeline 与真实张量链路。
4. **长尾优化必须服从时序约束。** 在时序任务中，按 scene 重采样通常比单帧重采样更合理。
5. **数据缺失要分型处置。** 能兜底的兜底、能补绑的补绑、无监督的剔除，避免全量重跑。
6. **评测协议是模型的一部分。** NMS、评测区域、score 权重、任务开关必须与训练版本绑定管理。
7. **量化结果必须描述口径。** 体素增量、GT IoU、标签缺失率和模型指标是不同维度，不能互相替代。
